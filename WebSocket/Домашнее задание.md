# WebSocket. Домашнее задание

## Конспект

При HTTP polling клиент через равные интервалы спрашивает сервер, появились ли изменения. Если сообщение в чате пришло сразу после очередной проверки, пользователь увидит его только при следующей. WebSocket позволяет серверу отправить сообщение сразу всем подключённым участникам. Клиент тоже может отправить данные в любой момент, пока соединение открыто. Такой режим называется полнодуплексным.

Классическое соединение WebSocket работает поверх TCP. Сначала браузер отправляет HTTP/1.1-запрос с заголовками `Connection: Upgrade` и `Upgrade: websocket`. Сервер подтверждает переход ответом `101 Switching Protocols`. Дальше по тому же соединению идут WebSocket-фреймы. Одно сообщение может состоять из нескольких фреймов. Библиотека собирает их, и приложение получает целое текстовое или двоичное сообщение.

Подключение асинхронное. После события `open` клиент может вызвать `send()`. Входящие данные приходят в событии `message`. На сервере Node.js события разных клиентов обрабатывает цикл событий, поэтому длительные синхронные вычисления задерживают обмен и у других участников.

Для штатного отключения сторона вызывает `close()`. Участники обмениваются управляющими фреймами Close, затем завершается TCP-соединение. Для проверки активности протокол предусматривает фреймы Ping и Pong. Если связь оборвалась, приложение узнаёт о закрытии через событие `close`.

В учебной работе сервер слушает только `127.0.0.1`, проверяет Origin браузера и принимает текст до 2048 байт. Клиент выводит полученные строки через `textContent`. Для передачи данных через сеть применяют TLS (`wss://`), а доступ к операциям проверяют на сервере.

## Ответы на вопросы

1. **Для чего используют WebSocket?** Для обмена событиями в реальном времени, например для доставки сообщений в чате или синхронизации правок в общем документе.
2. **Чем он отличается от HTTP polling?** При polling клиент повторяет запросы, в том числе когда новых данных нет. С WebSocket сервер посылает обновление по уже открытому соединению, как только оно появляется.
3. **Зачем нужен HTTP Upgrade?** В классическом варианте клиент предлагает серверу перейти с HTTP/1.1 на WebSocket в рамках текущего соединения.
4. **Что означает статус 101?** Сервер принял предложение сменить протокол. После проверки ответа браузер завершает рукопожатие и сообщает об открытии соединения.
5. **Чем отличаются ws и wss?** `ws://` передаёт данные без TLS. `wss://` использует TLS для шифрования, контроля целостности и проверки подлинности сервера.
6. **Что делает socket.send()?** Ставит текст или двоичные данные в очередь на отправку по открытому соединению. Получение сообщения другой стороной можно подтвердить ответом приложения, например эхом.
7. **Какие бывают состояния readyState?** `0 CONNECTING` — идёт подключение, `1 OPEN` — можно отправлять данные, `2 CLOSING` — началось закрытие, `3 CLOSED` — соединение закрыто либо подключение не удалось.
8. **Чем сообщение отличается от события data у TCP-сокета?** TCP доставляет поток байтов. Две отправленные строки могут прийти одним фрагментом, а одна строка — несколькими. WebSocket сохраняет границы сообщений, поэтому одному текстовому сообщению соответствует одно событие `message`.
9. **Почему JSON необязателен?** Формат содержимого выбирает приложение. В этой практике строка `PING` передаётся обычным текстом. Другие приложения могут передавать JSON или двоичные данные.
10. **Чем Ping/Pong отличаются от команды приложения?** Протокольный Ping имеет специальный тип фрейма, и получатель отвечает Pong на уровне протокола. Строка `PING` приходит обработчику `message`, который в нашей программе отвечает `ECHO: PING`.
11. **Зачем проверять входящие данные?** Клиент может прислать пустой текст, двоичные данные вместо текста или слишком большой объём. Проверка типа, содержимого и размера защищает обработчик от неподходящих данных и ограничивает расход памяти.
12. **Какие события обрабатывать при отключении?** В `close` фиксируют код и причину, освобождают связанные с клиентом ресурсы и обновляют интерфейс. В `error` регистрируют ошибку связи. При штатном закрытии достаточно события `close`.

## Практика. Проверка Echo-сервера

1. В папке WebSocket запустить `node server.mjs`. Если проект перенесли без папки `node_modules`, сначала выполнить `npm install`.
2. Открыть в браузере [локальный клиент](http://127.0.0.1:3061). Нажать F12, открыть **Network → WS**, затем на странице нажать **Подключиться**.
3. Выбрать соединение `ws`. В **Headers** проверить статус `101 Switching Protocols`. Во вкладке **Messages** проследить за обменом, по очереди отправляя строки из таблицы.

| Отправлено клиентом | Получено от сервера |
| --- | --- |
| PING | ECHO: PING |
| Привет, сервер! | ECHO: Привет, сервер! |
| Проверка связи | ECHO: Проверка связи |

4. Нажать **Отключиться**. Кнопка вызывает `socket.close(1000, 'Практика завершена')`. Состояние переходит из OPEN в CLOSING, отправка блокируется. После обмена фреймами Close соединение переходит в CLOSED. Клиент выводит код 1000 и причину, а сервер регистрирует отключение. Теперь можно подключиться повторно. Чтобы остановить сервер в терминале, нажать Ctrl+C.

### Сравнение способов обмена

| Механизм | Кто начинает обмен | Границы данных | Завершение |
| --- | --- | --- | --- |
| HTTP-запрос через fetch() | Клиент отправляет запрос, сервер отвечает | HTTP задаёт границы запроса и ответа | Обмен завершён после получения ответа и его тела. Транспортное соединение может использоваться повторно |
| TCP через node:net | Клиент устанавливает соединение, затем обе стороны могут писать независимо | Приложение само выделяет сообщения, например по переводу строки или префиксу длины | Вызов end() завершает отправку одной стороны. После завершения обеих сторон сокет закрывается |
| WebSocket | Клиент открывает соединение, затем любая сторона может отправить сообщение | Протокол задаёт границы сообщений с помощью фреймов | При штатном завершении стороны обмениваются Close, после чего закрывается транспорт |
